1. DESCRIPCIÓN GENERAL
================================================================================

Agent_T_T es un backend Flask que funciona como agente virtual de WhatsApp
para el programa Talento Tech del MinTIC (Colombia). Permite:

- Recibir mensajes de WhatsApp y responder automáticamente con IA (Gemini)
- Envío masivo de mensajes de plantilla a estudiantes
- Confirmación de matrícula (Sí/No) con registro en base de datos
- Consultas de estado de inscripción
- FAQs automáticas sobre el programa
- Sincronización bidireccional con Google Drive
- Panel de gestión vía API REST

Stack: Python 3.10+ | Flask 3.0 | LangGraph | Gemini 2.5 | Turso (libSQL)
Deploy: Render (backend) | Vercel (frontend)
URL producción: https://agent-t-t.onrender.com

4. FLUJOS DE TRABAJO DETALLADOS
================================================================================

────────────────────────────────────────────────────────────────────────────────
FLUJO 1: MENSAJE ENTRANTE DE WHATSAPP (MODO IA)
────────────────────────────────────────────────────────────────────────────────

1. Meta envía POST a /webhook con JSON del mensaje
2. webhook_controller.py:
   a. Parsea JSON
   b. Ignora si es status (sent/delivered/read)
   c. Extrae: message_id, from_number, text, type
   d. Verifica deduplicación (MessageDeduplicator)
   e. Si duplicado → responde 200 y termina
   f. Si nuevo → responde 200 inmediato + lanza thread background

3. process_message_background():
   a. Crea HumanMessage con el texto
   b. Invoca agent.invoke({messages, phone})

4. Grafo LangGraph ejecuta:
   a. load_context_node: busca estudiante por teléfono en Turso
      → Setea student_name y student_data en state
   
   b. router (clasificación de intención):
      PRIORIDAD 1 - Confirmación estricta:
        Si estado_envio='sent' Y respuesta='default' → CONFIRM
      
      PRIORIDAD 2 - Fast-Path (keywords, sin IA):
        'estado','matrícula' → STATUS
        'acceso','plataforma','clave' → ACCESS
        'hola','buenos días' (< 30 chars) → SALUDO
        'gracias' → GRACIAS
        'ok','listo','perfecto' → OK  
        'chao','adiós' → DESPEDIDA
        'qué es talento' → INFO_TALENTO
        'inscribirme','registrarme' → INFO_INSCRIPCION
        'bootcamp','cursos' → INFO_BOOTCAMPS
        'horario','duración' → INFO_HORARIO
        'certificado','diploma' → INFO_CERTIFICADO
        'gratis','costo' → INFO_COSTO
        'contacto','soporte' → INFO_CONTACTO
      
      PRIORIDAD 3 - Gemini (solo si nada matchea):
        Prompt: "Clasifica: STATUS, ACCESS o GENERAL"
        Gemini responde → se limpia a STATUS/ACCESS/GENERAL
   
   c. decide_next_node: enruta al nodo correspondiente
   
   d. Nodo ejecuta y retorna AIMessage con respuesta

5. WhatsApp envía la respuesta al usuario

────────────────────────────────────────────────────────────────────────────────
FLUJO 2: CONFIRMACIÓN DE MATRÍCULA (Sí/No)
────────────────────────────────────────────────────────────────────────────────

Condición: estado_envio='sent' AND respuesta IN ('default', '', NULL)

1. Router detecta modo confirmación estricta → intent=CONFIRM
2. confirm_response_node:
   a. Extrae texto del mensaje
   b. Detecta respuesta con patterns:
      Sí: ['sí','si','yes','acepto','confirmo','ok','dale','claro','listo']
      No: ['no','rechazo','cancelar','cancela','rechazar']
   c. Si no matchea → pide "responde SÍ o NO"
   d. Verifica que no haya respondido antes
   e. Guarda en BD: db_handler.update_respuesta(phone, respuesta, fecha)
   f. Responde con mensaje de confirmación o rechazo

────────────────────────────────────────────────────────────────────────────────
FLUJO 3: CONSULTA DE ESTADO
────────────────────────────────────────────────────────────────────────────────

1. Router detecta keywords de estado → intent=STATUS
2. check_status_node (DETERMINÍSTICO, sin IA):
   a. Lee campo 'respuesta' de student_data
   b. Tres casos:
      - respuesta='sí'/'si'/'yes' → "Tu cupo está CONFIRMADO"
      - respuesta='no' → "Indicaste que no participarás"  
      - respuesta='default'/vacío → "Aún no has confirmado. Responde SÍ o NO"
   c. Incluye: bootcamp, modalidad, fecha inicio

────────────────────────────────────────────────────────────────────────────────
FLUJO 4: ACCESO A PLATAFORMA
────────────────────────────────────────────────────────────────────────────────

1. Router detecta keywords de acceso → intent=ACCESS
2. platform_access_node:
   a. Si no tiene datos → "primero debes estar inscrito"
   b. Si confirmó o tiene opt_in=TRUE o matriculado:
      → Entrega credenciales: URL + usuario(cédula) + clave(cédula)
   c. Si no confirmó → "tu acceso aún no está habilitado"

────────────────────────────────────────────────────────────────────────────────
FLUJO 5: RESPUESTAS RÁPIDAS (0 tokens)
────────────────────────────────────────────────────────────────────────────────

1. Router Fast-Path detecta intent simple
2. quick_response_node retorna respuesta pre-definida:
   - SALUDO: menú de opciones
   - GRACIAS: agradecimiento
   - OK: confirmación genérica  
   - DESPEDIDA: despedida
   - INFO_TALENTO: qué es el programa
   - INFO_INSCRIPCION: pasos para inscribirse
   - INFO_BOOTCAMPS: lista de bootcamps disponibles
   - INFO_HORARIO: L-V 6pm-10pm, ~2 meses
   - INFO_CERTIFICADO: certificado MinTIC, 75% asistencia
   - INFO_COSTO: 100% gratuito
   - INFO_CONTACTO: soporte@talentotech.gov.co

────────────────────────────────────────────────────────────────────────────────
FLUJO 6: CONSULTA GENERAL (CON IA)
────────────────────────────────────────────────────────────────────────────────

1. Router no pudo clasificar → intent=GENERAL (o Gemini devuelve GENERAL)
2. llm_fallback_node:
   a. Construye prompt con base de conocimiento compacta de Talento Tech
   b. Invoca Gemini (gemini-2.5-flash-lite, temp=0.3)
   c. invoke_with_logging logea tokens usados
   d. Retorna respuesta de Gemini en formato WhatsApp

────────────────────────────────────────────────────────────────────────────────
FLUJO 7: ENVÍO MASIVO
────────────────────────────────────────────────────────────────────────────────

1. Frontend o API llama POST /api/messages/send-batch
2. message_controller.py:
   a. Obtiene pendientes: db_handler.get_estudiantes_pendientes_envio()
      Condición: opt_in IN ('TRUE','1','YES','SI') AND estado_envio != 'sent'
   b. Para cada estudiante:
      - Construye parámetros de plantilla (nombre, modalidad, bootcamp, etc.)
      - Envía: whatsapp_service.send_template_message()
      - Actualiza BD: db_handler.update_estado_envio('sent' o 'error')
      - Espera DELAY_SECONDS entre envíos (rate limiting)
   c. Retorna resumen de resultados

────────────────────────────────────────────────────────────────────────────────
FLUJO 8: CARGA DESDE GOOGLE DRIVE
────────────────────────────────────────────────────────────────────────────────

1. Frontend envía POST /api/google/upload con {fileId, accessToken}
2. drive_controller.py:
   a. Obtiene metadata del archivo (nombre, tipo MIME)
   b. Descarga contenido (CSV o Sheet exportado como CSV)
   c. Parsea con parse_file_content (sanitización agresiva)
   d. Normaliza: teléfonos a E.164, limpia caracteres
   e. Agrega columnas de tracking
   f. Valida estructura
   g. Inserta/actualiza en Turso (bootcamps + estudiantes)
   h. Actualiza columnas nuevas en el archivo original de Drive
   i. Configura sync automático con sync_service.set_current_file()

────────────────────────────────────────────────────────────────────────────────
FLUJO 9: SINCRONIZACIÓN AUTOMÁTICA
────────────────────────────────────────────────────────────────────────────────

1. APScheduler ejecuta _sync_job cada 5 minutos
2. Si hay pending_sync=True Y hay credenciales cacheadas:
   a. Lee todos los estudiantes de Turso
   b. Convierte a DataFrame
   c. Actualiza archivo en Drive según tipo MIME
   d. Marca pending_sync=False

────────────────────────────────────────────────────────────────────────────────
FLUJO 10: MODO LEGACY (SIN IA)
────────────────────────────────────────────────────────────────────────────────

Cuando USE_AI_AGENT=False en .env:
1. Webhook recibe mensaje
2. ResponseLogic.process_webhook_event(body) ejecuta:
   a. Extrae texto del mensaje
   b. Verifica si ya respondió (get_respuesta_existente)
   c. Regex: si/sí/yes/confirmar/acepto → guarda "Si"
   d. Regex: no/rechazar/cancelar → guarda "No"
   e. Otro → "responde SÍ o NO"
   f. Envía respuesta vía whatsapp_service

7. FUNCIONES RELEVANTES POR ARCHIVO
================================================================================

──── app/__init__.py ────
create_app()                        → Factory Flask: inicia servicios, blueprints
  Instancias globales: whatsapp_service, db_handler, sync_service, logic_brain

──── app/agent/graph.py ────
router(state) → {"intent": str}     → Clasifica intención del mensaje
  - Prioridad 1: confirmación estricta (estado_envio=sent + respuesta=default)
  - Prioridad 2: fast-path por keywords (~18 categorías)
  - Prioridad 3: Gemini (prompt clasificador → STATUS/ACCESS/GENERAL)
decide_next_node(state) → str       → Mapea intent a nombre de nodo
build_agent_graph() → CompiledGraph → Construye el grafo LangGraph
get_agent() → CompiledGraph         → Singleton del agente compilado

──── app/agent/state.py ────
AgentState(TypedDict)               → Estado del grafo:
  messages: List[dict]              → Historial (add_messages reducer)
  phone: str                        → Teléfono del usuario
  student_name: Optional[str]       → Nombre del estudiante
  student_data: Optional[dict]      → Datos completos del estudiante
  intent: Optional[str]             → Intención clasificada

──── app/agent/nodes/load_context.py ────
load_context_node(state)            → Busca estudiante en BD por teléfono
  Input: state['phone']
  Output: {student_name, student_data}

──── app/agent/nodes/status.py ────
check_status_node(state)            → Respuesta determinística de estado
  Lee: student_data['respuesta']
  Si 'sí/si/yes' → cupo confirmado
  Si 'no' → cupo cancelado
  Si 'default'/vacío → pendiente de confirmar
  NO USA IA

──── app/agent/nodes/platform.py ────
platform_access_node(state)         → Info de acceso a plataforma
  Si confirmó/opt_in/matriculado → credenciales
  Si no → "acceso no habilitado"
  NO USA IA

──── app/agent/nodes/confirm.py ────
confirm_response_node(state)        → Procesa Sí/No y guarda en BD
  Patterns Sí: sí, si, yes, acepto, confirmo, ok, dale, claro, listo
  Patterns No: no, rechazo, cancelar, cancela, rechazar
  Guarda: db_handler.update_respuesta(phone, respuesta, fecha)
  Verifica doble respuesta
  NO USA IA

──── app/agent/nodes/quick_response.py ────
quick_response_node(state)          → Respuestas pre-definidas (0 tokens)
  Mapa de 11 intents → strings estáticos
  NO USA IA

──── app/agent/nodes/fallback.py ────
llm_fallback_node(state)            → FAQ con Gemini
  Modelo: gemini-2.5-flash-lite (temp=0.3)
  Prompt: base de conocimiento compacta + pregunta
  Usa: invoke_with_logging() para tracking de tokens
  USA IA (última opción)

8. MODELOS DE IA UTILIZADOS
================================================================================

Se usa Google Gemini a través de langchain-google-genai:

1. ROUTER (graph.py)
   Modelo: gemini-2.5-flash-lite
   Temperatura: 0.0 (máxima precisión)
   Max tokens: 10 (solo 1 palabra: STATUS/ACCESS/GENERAL)
   Uso: SOLO cuando fast-path no matcheó (~5% de mensajes)

2. FAQ/FALLBACK (fallback.py)
   Modelo: gemini-2.5-flash-lite
   Temperatura: 0.3 (algo de creatividad)
   Max tokens: default
   Uso: consultas generales no cubiertas por nodos determinísticos

3. Nodos sin IA (0 tokens):
   - check_status_node: respuesta determinística
   - platform_access_node: respuesta determinística
   - confirm_response_node: pattern matching
   - quick_response_node: strings pre-definidos

13. NOTAS PARA DEPURACIÓN Y MEJORAS
================================================================================

PUNTOS DE ATENCIÓN:
- El router tiene ~18 categorías de fast-path pero los keywords son fijos
  (no aprende de nuevas variantes)
- El campo 'respuesta' en BD puede ser: 'Sí', 'No', 'default', '', NULL
  (inconsistencia entre mayúsculas/minúsculas según de dónde se setee)
- La lógica legacy (ResponseLogic) sigue activa como fallback cuando
  USE_AI_AGENT=False
- Los logs de tokens pueden mostrar 0/0/0 si la versión de langchain
  cambia el formato de response_metadata
- sync_service cachea el token de Google Drive en memoria (se pierde
  al reiniciar el dyno de Render)
- El template de WhatsApp ('prueba_matricula') tiene 8 parámetros fijos
  en el body que deben coincidir con la plantilla aprobada en Meta
- No hay autenticación en los endpoints REST (excepto webhook)
- db_handler usa REPLACE() en la WHERE para normalizar teléfonos
  en cada consulta (podría optimizarse con un campo normalizado)
- El deduplicador usa archivo JSON en /data/ para multi-worker sync,
  pero Gunicorn workers compiten por el lock del archivo
