1. DESCRIPCIÓN GENERAL
================================================================================

Agent_T_T es un backend Flask que funciona como agente virtual de WhatsApp
para el programa Talento Tech del MinTIC (Colombia). Permite:

- Recibir mensajes de WhatsApp y responder automáticamente con IA (Gemini)
- Envío masivo de mensajes de plantilla a estudiantes
- Confirmación de matrícula (Sí/No) con registro en base de datos
- Sistema de Campañas multi-tipo (MATRICULA, EVENTO, INFO)
- Confirmación de asistencia a eventos (Asisto/No Asisto)
- Consultas de estado de inscripción
- FAQs automáticas sobre el programa
- Sincronización bidireccional con Google Drive
- Panel de gestión vía API REST

Stack: Python 3.10+ | Flask 3.0 | LangGraph | Gemini 2.5 | Turso (libSQL)
Deploy: Render (backend) | Vercel (frontend)
URL producción: https://agent-t-t.onrender.com

4. FLUJOS DE TRABAJO DETALLADOS
================================================================================

────────────────────────────────────────────────────────────────────────────────
FLUJO 1: MENSAJE ENTRANTE DE WHATSAPP (MODO IA)
────────────────────────────────────────────────────────────────────────────────

1. Meta envía POST a /webhook con JSON del mensaje
2. webhook_controller.py:
   a. Parsea JSON
   b. Ignora si es status (sent/delivered/read)
   c. Extrae: message_id, from_number, timestamp, type
   d. Filtro de tiempo: si mensaje >5 min antiguo → descarta (evita reintentos de Meta)
   e. Verifica deduplicación atómica en RAM (MessageDeduplicator)
   f. Si duplicado → responde 200 y termina
   g. Extrae texto según tipo:
      - text: body directo
      - interactive/button_reply: título del botón
      - interactive/list_reply: título de la opción
      - button (legacy): texto del botón
   h. Si nuevo → responde 200 inmediato + lanza thread background (daemon)

3. process_message_background():
   a. Crea HumanMessage con el texto
   b. Invoca agent.invoke({messages, phone})

4. Grafo LangGraph ejecuta:
   a. load_context_node: busca estudiante por teléfono en Turso
      → Setea student_name y student_data en state
      → Busca campaña activa: db_handler.get_campana_activa_for_student()
      → Setea active_campaign en state (o None si no hay)
   
   b. router (clasificación de intención):
      PRIORIDAD 0 - Campaña activa:
        Si active_campaign existe con campana_tipo='EVENTO' y sin respuesta → CONFIRM_EVENT
        Si active_campaign existe con campana_tipo='MATRICULA' y sin respuesta → CONFIRM
      
      PRIORIDAD 2 - Fast-Path (keywords, sin IA):
        'estado','matrícula' → STATUS
        'acceso','plataforma','clave' → ACCESS
        'hola','buenos días' (< 30 chars) → SALUDO
        'gracias' → GRACIAS
        'ok','listo','perfecto' → OK  
        'chao','adiós' → DESPEDIDA
        'qué es talento' → INFO_TALENTO
        'inscribirme','registrarme' → INFO_INSCRIPCION
        'bootcamp','cursos' → INFO_BOOTCAMPS
        'horario','duración' → INFO_HORARIO
        'certificado','diploma' → INFO_CERTIFICADO
        'gratis','costo' → INFO_COSTO
        'contacto','soporte' → INFO_CONTACTO
      
      PRIORIDAD 3 - Gemini (solo si nada matchea):
        Prompt: "Clasifica: STATUS, ACCESS o GENERAL"
        Gemini responde → se limpia a STATUS/ACCESS/GENERAL
   
   c. decide_next_node: enruta al nodo correspondiente
      CONFIRM_EVENT → confirm_event (campañas de evento)
      CONFIRM → confirm_response (matrícula via campaña activa)
   
   d. Nodo ejecuta y retorna AIMessage con respuesta

5. WhatsApp envía la respuesta al usuario

────────────────────────────────────────────────────────────────────────────────
FLUJO 2: CONFIRMACIÓN DE MATRÍCULA (Sí/No)
────────────────────────────────────────────────────────────────────────────────

Condición: Existe campaña activa tipo MATRICULA con envío hecho y sin respuesta
           (detectada por get_campana_activa_for_student en load_context)

1. Router detecta active_campaign con campana_tipo='MATRICULA' → intent=CONFIRM
2. confirm_response_node:
   a. Extrae texto del mensaje
   b. Detecta respuesta con patterns:
      Sí: ['sí','si','yes','acepto','confirmo','ok','dale','claro','listo']
      No: ['no','rechazo','cancelar','cancela','rechazar']
   c. Si no matchea → pide "responde SÍ o NO"
   d. Verifica estado_academico (MATRICULADO/RECHAZADO/GRADUADO = ya respondió)
   e. Guarda en BD: db_handler.update_respuesta(phone, respuesta, fecha)
      → Actualiza estado_academico (INSCRITO→MATRICULADO o INSCRITO→RECHAZADO)
      → Actualiza campana_miembros si hay campaña activa
   f. Responde con mensaje de confirmación o rechazo

────────────────────────────────────────────────────────────────────────────────
FLUJO 2.5: CONFIRMACIÓN DE ASISTENCIA A EVENTO (Asisto/No Asisto)
────────────────────────────────────────────────────────────────────────────────

Condición: Existe campaña activa tipo EVENTO con envío hecho y sin respuesta
           (detectada por get_campana_activa_for_student en load_context)

1. load_context_node carga active_campaign desde campana_miembros
2. Router detecta active_campaign con campana_tipo='EVENTO' sin respuesta
   → intent=CONFIRM_EVENT (PRIORIDAD 0, antes que matrícula)
3. confirm_event_node:
   a. Valida que hay campaña activa
   b. Verifica que no haya respondido antes (doble validación)
   c. Detecta respuesta con patterns:
      Asiste: ['asisto','asistiré','voy','iré','confirmo','sí','dale','ok','claro','acepto','cuenten conmigo']
      No Asiste: ['no asisto','no asistiré','no voy','no puedo','no','rechazo','cancelar','paso','imposible']
      → Primero verifica no_asiste (más específicos) para evitar false positive con "no"
   d. Si no matchea → pide "responde Asisto o No Asisto"
   e. Guarda en campana_miembros: db_handler.update_miembro_respuesta(miembro_id, respuesta, raw_text)
   f. NO TOCA tabla estudiantes (diseño crítico: evento ≠ matrícula)
   g. Responde con confirmación positiva o registro de no asistencia
   f. Responde con mensaje de confirmación o rechazo

────────────────────────────────────────────────────────────────────────────────
FLUJO 3: CONSULTA DE ESTADO
────────────────────────────────────────────────────────────────────────────────

1. Router detecta keywords de estado → intent=STATUS
2. check_status_node (DETERMINÍSTICO, sin IA):
   a. Lee campo 'estado_academico' de student_data
   b. Cuatro casos:
      - MATRICULADO → "Tu cupo está CONFIRMADO" + fecha inicio
      - RECHAZADO → "Indicaste que no participarás"
      - GRADUADO → "Completaste exitosamente el bootcamp"
      - INSCRITO (u otro) → "Aún no has confirmado. Responde SÍ o NO"
   c. Incluye: bootcamp_nombre, modalidad, fecha_inicio_tecnica

────────────────────────────────────────────────────────────────────────────────
FLUJO 4: ACCESO A PLATAFORMA
────────────────────────────────────────────────────────────────────────────────

1. Router detecta keywords de acceso → intent=ACCESS
2. platform_access_node:
   a. Si no tiene datos → "primero debes estar inscrito"
   b. Si estado_academico IN ('MATRICULADO', 'GRADUADO'):
      → Entrega credenciales: URL + usuario(cédula) + clave(cédula)
   c. Si estado_academico no es MATRICULADO/GRADUADO → "tu acceso aún no está habilitado"

────────────────────────────────────────────────────────────────────────────────
FLUJO 5: RESPUESTAS RÁPIDAS (0 tokens)
────────────────────────────────────────────────────────────────────────────────

1. Router Fast-Path detecta intent simple
2. quick_response_node retorna respuesta pre-definida:
   - SALUDO: menú de opciones
   - GRACIAS: agradecimiento
   - OK: confirmación genérica  
   - DESPEDIDA: despedida
   - INFO_TALENTO: qué es el programa
   - INFO_INSCRIPCION: pasos para inscribirse
   - INFO_BOOTCAMPS: lista de bootcamps disponibles
   - INFO_HORARIO: L-V 6pm-10pm, ~2 meses
   - INFO_CERTIFICADO: certificado MinTIC, 75% asistencia
   - INFO_COSTO: 100% gratuito
   - INFO_CONTACTO: soporte@talentotech.gov.co

────────────────────────────────────────────────────────────────────────────────
FLUJO 6: CONSULTA GENERAL (CON IA)
────────────────────────────────────────────────────────────────────────────────

1. Router no pudo clasificar → intent=GENERAL (o Gemini devuelve GENERAL)
2. llm_fallback_node:
   a. Construye prompt con base de conocimiento compacta de Talento Tech
   b. Invoca Gemini (gemini-2.5-flash-lite, temp=0.3)
   c. invoke_with_logging logea tokens usados
   d. Retorna respuesta de Gemini en formato WhatsApp

────────────────────────────────────────────────────────────────────────────────
FLUJO 7: ENVÍO MASIVO
────────────────────────────────────────────────────────────────────────────────

1. Frontend o API llama POST /api/messages/send-batch
2. message_controller.py:
   a. Crea campaña implícita tipo MATRICULA
   b. Agrega miembros: estudiantes con opt_in=1 pendientes
   c. Para cada miembro pendiente:
      - Construye parámetros de plantilla (nombre, modalidad, bootcamp, etc.)
      - Envía: whatsapp_service.send_template_message()
      - Actualiza campana_miembros: estado_envio='sent' o 'error'
      - Espera DELAY_SECONDS entre envíos (rate limiting)
   d. Retorna resumen de resultados

────────────────────────────────────────────────────────────────────────────────
FLUJO 8: CARGA DESDE GOOGLE DRIVE
────────────────────────────────────────────────────────────────────────────────

1. Frontend envía POST /api/google/upload con {fileId, accessToken}
2. drive_controller.py:
   a. Obtiene metadata del archivo (nombre, tipo MIME)
   b. Descarga contenido (CSV o Sheet exportado como CSV)
   c. Parsea con parse_file_content (sanitización agresiva)
   d. Normaliza: teléfonos a E.164, limpia caracteres
   e. Agrega columnas de tracking
   f. Valida estructura
   g. Inserta/actualiza en Turso (bootcamps + estudiantes)
   h. Actualiza columnas nuevas en el archivo original de Drive
   i. Configura sync automático con sync_service.set_current_file()

────────────────────────────────────────────────────────────────────────────────
FLUJO 9: SINCRONIZACIÓN AUTOMÁTICA
────────────────────────────────────────────────────────────────────────────────

1. APScheduler ejecuta _sync_job cada 5 minutos
2. Si hay pending_sync=True Y hay credenciales cacheadas:
   a. Lee todos los estudiantes de Turso
   b. Convierte a DataFrame
   c. Actualiza archivo en Drive según tipo MIME
   d. Marca pending_sync=False

────────────────────────────────────────────────────────────────────────────────
FLUJO 10: MODO LEGACY (SIN IA)
────────────────────────────────────────────────────────────────────────────────

Cuando USE_AI_AGENT=False en .env:
1. Webhook recibe mensaje
2. ResponseLogic.process_webhook_event(body) ejecuta:
   a. Extrae texto del mensaje
   b. Verifica si ya respondió (get_respuesta_existente)
   c. Regex: si/sí/yes/confirmar/acepto → guarda "Si"
   d. Regex: no/rechazar/cancelar → guarda "No"
   e. Otro → "responde SÍ o NO"
   f. Envía respuesta vía whatsapp_service

5. ENDPOINTS REST COMPLETOS
================================================================================

────────────── SISTEMA ──────────────
GET  /                              → Info general de la API
GET  /health                        → Health check (credenciales + BD)
GET  /privacy                       → Política de privacidad (HTML)
DELETE /api/database/reset          → [PELIGRO] Borra TODA la BD

────────────── WEBHOOK ──────────────
GET  /webhook                       → Verificación handshake con Meta
     Params: hub.mode, hub.verify_token, hub.challenge
POST /webhook                       → Recepción de mensajes/eventos WhatsApp

────────────── MENSAJES ──────────────
POST /api/messages/send-simple      → Envía mensaje texto o plantilla
     Body: {phone, message} o {phone, template_name, parameters, language_code}
POST /api/messages/send-template    → Alias de send-simple (legacy)
POST /api/messages/send-batch       → Envío masivo a todos los pendientes
     Body: {template_name?, language_code?}

────────────── ESTUDIANTES ──────────────
GET  /api/estudiantes/all           → Lista paginada
     Params: limit (default 100), offset (default 0)
GET  /api/estudiantes/bootcamp/<id> → Filtrar por bootcamp
GET  /api/estudiantes/phone/<phone> → Buscar por teléfono
PUT  /api/estudiantes/update-field  → Actualizar campo específico
     Body: {telefono, field, value}
DELETE /api/estudiantes/delete/<phone> → Eliminar estudiante

────────────── ESTADÍSTICAS ──────────────
GET  /api/estadisticas              → Stats generales (alias)
GET  /api/contacts/stats            → Stats generales
     Response: {total_estudiantes, mensajes_enviados, mensajes_error,
                confirmaron_si, confirmaron_no, pendientes_respuesta,
                total_bootcamps, tasa_respuesta}
GET  /api/contacts/pending          → Lista de pendientes de envío

────────────── BOOTCAMPS ──────────────
GET  /api/bootcamps                 → Lista todos los bootcamps
DELETE /api/bootcamps/delete/<id>   → Eliminar un bootcamp
DELETE /api/bootcamps/clear-all     → [PELIGRO] Eliminar todos los bootcamps

────────────── GOOGLE DRIVE ──────────────
POST /api/google/upload             → Procesar archivo de Drive
     Body: {fileId, accessToken}
POST /api/sync/drive-manual         → Forzar sincronización manual

────────────── CAMPAÑAS ──────────────
POST /api/campaigns                 → Crear campaña
     Body: {nombre, tipo (MATRICULA|EVENTO|INFO), plantilla_whatsapp?, bootcamp_objetivo_id?}
GET  /api/campaigns                 → Listar todas las campañas
GET  /api/campaigns/<id>            → Obtener campaña con estadísticas
POST /api/campaigns/<id>/members    → Agregar miembros
     Body opción 1: {estudiante_ids: [1,2,3]}
     Body opción 2: {bootcamp_id: "IA_2024_01"}
     Body opción 3: {all_opt_in: true}
POST /api/campaigns/<id>/send       → Enviar campaña a pendientes
     Body: {language_code?: "es", has_header_param?: false}
GET  /api/campaigns/<id>/stats      → Estadísticas detalladas
DELETE /api/campaigns/<id>          → Eliminar campaña + miembros

13. NOTAS PARA DEPURACIÓN Y MEJORAS
================================================================================

PUNTOS DE ATENCIÓN:
- El router tiene ~18 categorías de fast-path pero los keywords son fijos
  (no aprende de nuevas variantes)
- El campo 'estado_academico' en BD es: 'INSCRITO', 'MATRICULADO', 'RECHAZADO', 'GRADUADO'
  (valores enum controlados por update_respuesta y lógica del agente)
- Los datos de envío/respuesta de campañas se guardan en campana_miembros,
  NO en la tabla estudiantes (diseño normalizado v3)
- La tabla estudiantes ya NO tiene: estado_envio, message_id, respuesta,
  fecha_envio, fecha_respuesta, bootcamp_nombre, modalidad, horario, lugar,
  ingles_inicio, ingles_fin, inicio_formacion (movidos a bootcamps o campana_miembros)
- La lógica legacy (ResponseLogic) sigue activa como fallback cuando
  USE_AI_AGENT=False
- Los logs de tokens pueden mostrar 0/0/0 si la versión de langchain
  cambia el formato de response_metadata
- sync_service cachea el token de Google Drive en memoria (se pierde
  al reiniciar el dyno de Render)
- El template de WhatsApp ('prueba_matricula') tiene 8 parámetros fijos
  en el body que deben coincidir con la plantilla aprobada en Meta
- No hay autenticación en los endpoints REST (excepto webhook)
- db_handler usa REPLACE() en la WHERE para normalizar teléfonos
  en cada consulta (podría optimizarse con un campo normalizado)
- El deduplicador usa RAM pura con OrderedDict LRU (5000 entradas max,
  TTL 5 min). Optimizado para 1 worker Gunicorn con multi-threading.
  Sin File I/O para máxima velocidad.
- Webhook descarta mensajes con timestamp >5 min para evitar procesar
  reintentos antiguos de Meta
- SISTEMA DE CAMPAÑAS:
  * campanas + campana_miembros son tablas independientes de estudiantes
  * Las respuestas de EVENTO se guardan en campana_miembros, NO en estudiantes
  * Router asigna PRIORIDAD 0 a campañas activas (EVENTO y MATRICULA)
  * confirm_event_node verifica no_asiste_patterns ANTES de asiste_patterns
    para evitar false positives con la palabra "no" sola
  * Tipos soportados: MATRICULA, EVENTO, INFO (escalable para futuros tipos)
  * API de campañas en /api/campaigns sin autenticación (mismo que otros endpoints)
  * send_campaign usa DELAY_SECONDS entre envíos para rate limiting de Meta
